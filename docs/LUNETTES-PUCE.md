# Lunettes M01 Pro — la puce, le protocole, les outils

Recherche technique du 2026-09-04. Aucune manipulation n'a été faite sur les lunettes pour
écrire ce document : tout ce qui suit vient de sources publiques et du relevé déjà effectué
(`docs/LUNETTES-DIAGNOSTIC.md`).

Convention de lecture :

- **Établi** = vérifié dans une source que j'ai réellement ouverte, ou vérifié par le calcul.
- **Déduit** = raisonnement cohérent, mais pas de source qui l'affirme.
- **Non trouvé** = cherché, pas trouvé. Pas de conjecture déguisée.

## 1. Ce qui est établi

### 1.1 Le fabricant de la puce : Zhuhai Jieli (杰理)

L'identifiant Bluetooth SIG **`0x05D6`** correspond, dans la liste officielle des
Company Identifiers publiée par le Bluetooth SIG, à :

```yaml
  - value: 0x05D6
    name: 'Zhuhai Jieli technology Co.,Ltd'
```

Source : fichier officiel `company_identifiers.yaml` du dépôt public du Bluetooth SIG
(téléchargé et lu, ligne 7917).

Deux corroborations indépendantes, dans le code source publié par Jieli lui-même
(dépôt `Jieli-Tech/fw-AC63_BT_SDK`) :

- `apps/spp_and_le/examples/conn_24g/ble_24g_server.c` :
  `#define EIR_TAG_STRING 0xd6, 0x05, 0x08, 0x00, 'J','L','A','I','S','D','K'`
  — Jieli émet `0x05D6` en petit-boutiste comme identifiant de société dans ses propres
  trames publicitaires, avec la marque « JLAISDK ».
- `apps/hid/modules/bt/ble_hogp.c` : `#define PNP_VID 0x05ac //0x05d6`
  — la valeur `0x05d6` figure en commentaire comme alternative « maison » à l'identifiant
  de démonstration.

**Conclusion : la puce des lunettes est un SoC audio Bluetooth Zhuhai Jieli.**
C'est le fournisseur chinois dominant des puces d'écouteurs et d'enceintes à bas coût
(familles AC63xx, AC69xx, AC70xx, AD1xN).

### 1.2 Le jeu d'UUID `ae30` / `ae01` / `ae02` / `ae03` est le profil BLE standard de Jieli

Le profil GATT relevé sur les lunettes est, caractéristique par caractéristique et propriété
par propriété, **exactement** celui du fichier
`apps/spp_and_le/examples/trans_data/ble_trans_profile.h` du SDK public Jieli AC63 :

| Relevé sur les lunettes | Dans le SDK Jieli (fichier ci-dessus) |
|---|---|
| service `ae30` | `// 0x0008 PRIMARY_SERVICE ae30` |
| `ae01` write-without-response | `/* CHARACTERISTIC, ae01, WRITE_WITHOUT_RESPONSE \| DYNAMIC */` |
| `ae02` notify | `/* CHARACTERISTIC, ae02, NOTIFY */` |
| `ae03` write-without-response | `/* CHARACTERISTIC, ae03, WRITE_WITHOUT_RESPONSE \| DYNAMIC */` |
| `ae04` notify | `/* CHARACTERISTIC, ae04, NOTIFY */` |
| `ae05` indicate | `/* CHARACTERISTIC, ae05, INDICATE */` |
| `ae10` read/write | `/* CHARACTERISTIC, ae10, READ \| WRITE \| DYNAMIC */` |
| service `ae3a` | `// 0x0040 PRIMARY_SERVICE ae3a` |
| `ae3b` write-without-response | `/* CHARACTERISTIC, ae3b, WRITE_WITHOUT_RESPONSE \| DYNAMIC */` |
| `ae3c` notify | `/* CHARACTERISTIC, ae3c, NOTIFY */` |

Le fichier porte l'en-tête : « gatt profile include file, generated by jieli
gatt_inc_generator.exe ». La correspondance est intégrale, y compris `ae10` qui renvoie une
valeur vide chez Jieli aussi (attribut dynamique sans contenu par défaut).

**Rôle de `ae30`** : canal de transmission transparente (« trans_data »), l'équivalent BLE
d'un port série. La documentation officielle Jieli le décrit ainsi : on active les
notifications sur `AE02` et `AE05`, on écrit sur `AE01` ou `AE03`, et les données ressortent
sur `AE02` / `AE05`.

**Rôle de `ae3a`** : second canal transparent, à plus fort débit. Dans le code du SDK
(`ble_trans.c`, fonction `trans_test_send_audio_data`), c'est **`ae3c` qui sert à pousser des
paquets audio de 128 octets** vers le téléphone, et `ae3b` qui reçoit les écritures.
Autrement dit : `ae30` = canal de commande, `ae3a` = canal de données/audio.

### 1.3 Il existe un troisième service Jieli, `ae00`, qui porte le protocole applicatif RCSP

Dans le même fichier, sous `#if RCSP_BTMATE_EN`, Jieli déclare un service **`ae00`** avec
`ae01` (write) et `ae02` (notify). C'est le service utilisé par les applications officielles
Jieli. Je l'ai vérifié en extrayant la bibliothèque `jl_bt_ota_V1.11.0_11015-release.aar`
du dépôt `Jieli-Tech/Android-JL_OTA` : la classe
`com.jieli.jl_bt_ota.constant.BluetoothConstant` contient

```
UUID_SERVICE       = 0000ae00-0000-1000-8000-00805F9B34FB
UUID_WRITE         = 0000ae01-0000-1000-8000-00805F9B34FB
UUID_NOTIFICATION  = 0000ae02-0000-1000-8000-00805F9B34FB
UUID_SPP           = 00001101-0000-1000-8000-00805F9B34FB
UUID_A2DP          = 0000110b-…   UUID_HFP = 0000111e-…
PROTOCOL_TYPE_BLE / PROTOCOL_TYPE_SPP / PROTOCOL_TYPE_GATT_OVER_BR_EDR
```

Les lunettes n'exposent **pas** `ae00` en BLE, mais elles exposent le SPP `00001101`.

### 1.4 Le protocole série de Jieli s'appelle RCSP, et son format de trame est public

Le SDK public contient l'en-tête `include_lib/btstack/third_party/rcsp/JL_rcsp_packet.h` :

```c
struct __JL_PACKET {
    u8          tag[3];
    HEAD_BIT    head;     // OpCode:8 | unused:6 | resp:1 | type:1
    u16         length;
    u8          data[0];
};
#define JL_PACK_START_TAG0  (0xfe)
#define JL_PACK_START_TAG1  (0xdc)
#define JL_PACK_START_TAG2  (0xba)
#define JL_PACK_END_TAG     (0xef)
```

Soit, sur le fil :

```
FE DC BA | drapeau (1) | opcode (1) | longueur (2, gros-boutiste) | corps | EF
```

Ce format est confirmé indépendamment par un projet de rétro-ingénierie extérieur à Jieli
(`hybridherbst/web-bluetooth-e87`, badge LED à puce Jieli), qui documente les mêmes octets et
précise les drapeaux : `0xC0` = commande, `0x00` = réponse, `0x80` = donnée.

La liste des opcodes est publique dans `JL_rcsp_protocol.h` du SDK. Extraits utiles :

| Opcode | Signification |
|---|---|
| `0x02` / `0x03` | lire la carte des fonctions supportées |
| `0x07` / `0x08` | lire / écrire une information système |
| `0x09` | remontée automatique d'information système |
| `0x0E` | commande de fonction |
| `0x19` | « find device » |
| `0x1B`–`0x1E` | transfert de fichier |
| `0x1F` / `0x20` | supprimer / renommer un fichier |
| `0x22` | **formatage de l'appareil** |
| `0xD1` | négociation de MTU |
| `0xFF` | commande client |

Les attributs lisibles sont listés dans le même fichier : version de protocole, infos système,
adresse EDR, plateforme, version, type de SDK, version d'UBOOT, double partition, statut de
mise à jour, VID/PID, clé d'authentification, code produit, MTU max, adresse BLE.

**Authentification** : RCSP comporte une phase d'authentification. La bibliothèque Android
contient une classe `com.jieli.jl_bt_ota.impl.RcspAuth` et une constante `JL_AUTH = "jl_ota_auth"`.
Le projet `web-bluetooth-e87` a reconstitué cet échange par rétro-ingénierie de `libjl_auth.so`
(chiffrement par blocs propriétaire, 16 tours, clé statique de 16 octets documentée dans le dépôt).
Sans cette poignée de main, certaines commandes RCSP sont refusées.

**Commandes AT** : le SDK contient un exemple `apps/spp_and_le/examples/at_char_com/at_char_cmds.c`
avec les en-têtes `"AT+"` et `"AT>"` et les commandes `GVER`, `GCFGVER`, `NAME`, `LBDADDR`,
`BAUD`, `ADV`, `ADVPARAM`, `ADVDATA`, `SRDATA`, `CONNPARAM`, `SCAN`, `TARGETUUID`, `CONN`,
`DISC`, `OTA`, `CONN_CANNEL`, `POWEROFF`, `LOWPOWER`. **Attention** : c'est un firmware
« module BLE piloté par UART », destiné à une liaison série filaire. Rien n'indique que les
lunettes exposent des commandes AT. Ne pas en attendre de miracle.

**L'octet `bc` n'appartient pas au monde Jieli.** Une trame RCSP commence par `FE DC BA`.
Les trames observées commencent par `BC`. Ce sont deux protocoles différents cohabitant dans
le même firmware.

### 1.5 L'octet `bc` : c'est le protocole « big data » de la famille Oudmon / Colmi

Les trois UUID « propriétaires » relevés sur les lunettes ne viennent pas de Jieli mais d'une
pile logicielle chinoise de wearables très répandue (l'application de référence est
`com.oudmon.ble.*`, éditeur Shenzhen Oudmon ; on la retrouve sur les bagues connectées
Colmi R02/R03/R06/R09/R10 et leurs clones).

Le projet Gadgetbridge, qui les supporte, définit exactement les UUID relevés
(`ColmiR0xConstants.java`) :

```java
CHARACTERISTIC_SERVICE_V1 = 6e40fff0-b5a3-f393-e0a9-e50e24dcca9e
CHARACTERISTIC_WRITE      = 6e400002-b5a3-f393-e0a9-e50e24dcca9e
CHARACTERISTIC_NOTIFY_V1  = 6e400003-b5a3-f393-e0a9-e50e24dcca9e
CHARACTERISTIC_SERVICE_V2 = de5bf728-d711-4e47-af26-65e3012a5dc7
CHARACTERISTIC_COMMAND    = de5bf72a-d711-4e47-af26-65e3012a5dc7   (écriture)
CHARACTERISTIC_NOTIFY_V2  = de5bf729-d711-4e47-af26-65e3012a5dc7   (notification)
CMD_BIG_DATA_V2           = (byte) 0xbc
BIG_DATA_TYPE_SLEEP       = 0x27
BIG_DATA_TYPE_SPO2        = 0x2a
```

C'est mot pour mot ce que les lunettes exposent. Le service `6e40fff0` n'est donc pas un
« Nordic UART bricolé » : c'est le canal V1 de cette pile, qui a emprunté la base d'UUID de
Nordic. Et `de5bf728` est son canal V2, dit « big data ».

### 1.6 Le format exact des trames `bc`, vérifié par le calcul

Gadgetbridge (`ColmiR0xDeviceSupport.java`) parse ainsi : `value[0]` = `0xbc`,
`value[1]` = type, `value[2..3]` = longueur sur 16 bits petit-boutiste, et il attend
« packetLength **+ 6** » octets. Il reste donc 2 octets d'en-tête non utilisés par
Gadgetbridge, en positions 4 et 5.

**J'ai identifié ces deux octets : c'est un CRC-16/MODBUS de la charge utile, transmis en
petit-boutiste.** Vérification numérique sur les trois trames relevées :

| Trame observée | Charge utile | CRC-16/MODBUS calculé | Octets attendus | Octets observés |
|---|---|---|---|---|
| `bc 73 03 00 5e 61 05 56 00` | `05 56 00` | `0x615E` | `5e 61` | `5e 61` ✔ |
| `bc 73 03 00 5e 91 05 55 00` | `05 55 00` | `0x915E` | `5e 91` | `5e 91` ✔ |
| `bc 73 03 00 5f 01 05 54 00` | `05 54 00` | `0x015F` | `5f 01` | `5f 01` ✔ |

Contre-épreuve sur une trame **écrite par Gadgetbridge** (requête d'historique SpO2, codée en
dur dans le source) : `bc 2a 01 00 ff 00 ff` — charge utile `ff`,
CRC-16/MODBUS(`ff`) = `0x00FF`, octets `ff 00`. ✔

**Format définitif :**

```
BC | type (1) | longueur (2, petit-boutiste) | CRC-16/MODBUS de la charge utile (2, petit-boutiste) | charge utile
```

En-tête de 6 octets. Polynôme `0x8005`, init `0xFFFF`, entrée et sortie réfléchies, pas de
XOR final.

### 1.7 Correction importante sur `docs/LUNETTES-DIAGNOSTIC.md`

Ce document décrit le format comme
`bc <type> <longueur> <données> <2 octets de contrôle>`, avec le contrôle **à la fin**.
C'est inexact : **les 2 octets de contrôle sont en positions 4-5, avant les données.**

Conséquence directe : ce que ce document appelait « les codes d'événement `c0 80` et `c6 d0` »
sont en réalité des CRC. J'ai retrouvé les charges utiles correspondantes par recherche
exhaustive :

| CRC observé (sur le fil) | Valeur CRC | Charge utile qui le produit |
|---|---|---|
| `c0 80` | `0x80C0` | `03 01` |
| `c6 d0` | `0xD0C6` | `0a 01` |

Les « deux événements qui alternent » sont donc les codes **`0x03`** et **`0x0A`**, chacun avec
la valeur `01`.

Précision honnête sur cette reconstitution : `03 01` et `0a 01` sont les **seules** solutions
sur une ou deux octets, et elles forment une paire cohérente (même second octet, deux codes
différents). Un CRC de 16 bits admet évidemment des collisions sur des charges utiles plus
longues — la recherche en a trouvé neuf sur trois octets pour chaque CRC, mais toutes
commencent par un premier octet aberrant (`a1`, `a2`, `a4`, `a7`, `a8`, `ab`, `ad`, `ae`, `b6`)
qui ne ressemble à aucun code d'événement. Le champ de longueur de ces trames n'ayant pas été
consigné dans le relevé précédent, la lecture à deux octets reste une **déduction très
probable**, pas un fait établi. Une nouvelle capture, avec les trames complètes, la confirmera
en une seconde. Les scripts `decoder-gestes-lunettes.py` doivent être corrigés pour découper la
trame au bon endroit, sinon ils étiquettent des CRC au lieu d'étiqueter des gestes.
(Je n'ai touché à aucun de ces fichiers.)

### 1.8 `fee1` = Anhui Huami, confirmé

Dans la liste officielle des 16-bit UUID membres du Bluetooth SIG (`member_uuids.yaml`) :
`0xFEE0` et `0xFEE1` = « Anhui Huami Information Technology Co., Ltd. ». C'est bien
l'attribution officielle. Sa présence ici est un emprunt : le fabricant réutilise un UUID qui
ne lui appartient pas, pratique courante. Le SDK Jieli ne contient rien en `fee1` (son module
Tencent LLSync utilise `0xFEE7` / `0xFEBA`, pas `fee1`).

## 2. Ce qui est déduit

Ces points sont cohérents mais aucune source ne les affirme.

1. **`VID&000105D6` se lit « source = Bluetooth SIG, fournisseur = 0x05D6 ».**
   Microsoft documente seulement que « les huit chiffres qui suivent `VID&` correspondent au
   code fournisseur » et que la pile ne génère un couple VID/PID que si l'appareil publie un
   enregistrement Plug and Play découvrable par SDP. Le découpage `0001` + `05D6` est la
   lecture standard de l'enregistrement Device ID (source 0x0001 = identifiant de société
   Bluetooth SIG). Le fait que `05D6` tombe pile sur Jieli rend la lecture très solide, mais
   je ne l'ai pas trouvée écrite noir sur blanc.

2. **`PID 0x000A`** est un identifiant produit choisi par le fabricant des lunettes, pas par
   Jieli. Sa faible valeur suggère un compteur interne. Aucune base publique ne référence les
   PID Jieli.

3. **Le firmware des lunettes combine deux piles logicielles.** Une base Jieli (audio,
   Bluetooth classique, profil `ae30`/`ae3a`, très probablement RCSP sur SPP) et un module
   applicatif d'origine Oudmon/Colmi (services `6e40fff0` et `de5bf728`, protocole `bc`), qui
   est celui qui parle réellement à l'application compagnon. C'est du logiciel assemblé par
   intégration, pratique courante chez les ODM de Shenzhen.

4. **La famille précise de la puce.** Le SDK où j'ai trouvé le profil couvre AC63xx « et les
   séries AC69 sans audio ». Comme les lunettes font de l'audio (A2DP + HFP), c'est plus
   probablement un AC69xx ou AC70xx. Je ne peux pas trancher sans lire la flash ou ouvrir la
   monture. Le `LUNETTES-DIAGNOSTIC.md` disait déjà « AC69xx / AC70xx » : c'est la bonne
   fourchette, mais ce n'est pas établi.

5. **Signification des trames `bc 73 …`** — voir section 4, c'est le point le plus utile.

## 3. Ce qui reste inconnu

- **`AM01C`** : non trouvé. Aucune occurrence publique de cette référence, ni comme produit,
  ni comme puce, ni comme carte. C'est très probablement un code interne d'ODM. Le format
  `AM01C_2.20.04_260122` se lit comme « plateforme + version + date 2026-01-22 », mais c'est
  une lecture, pas une source.

- **Le fabricant réel et l'application compagnon officielle** : non trouvés.
  « M01 » / « M01 Pro » est un nom de produit blanc revendu sous une dizaine de marques
  (Aovemt, OXIVUE, VISIOVOY, et des revendeurs génériques), et les notices trouvées décrivent
  des variantes **avec caméra** (une notice mentionne un processeur « JL7018F » — donc Jieli
  là aussi — et un capteur Sony IMX219), pas des lunettes purement audio comme celles-ci.
  L'application `com.smglassy.m01prosmartaiglassesapp` (« M01 pro Smart Ai Glasses »,
  éditeur « Vessel Service Solutions », mise à jour le 2026-07-10) existe bien sur Google Play,
  **mais sa propre fiche indique qu'elle n'est ni affiliée ni autorisée par un fabricant de
  lunettes**. Ce n'est donc pas l'application officielle. Le nom de paquet de l'application
  officielle : **non trouvé**.

- **Le service `3802` avec la caractéristique `4a02`** : non trouvé. Aucune attribution SIG
  (la plage membre commence à `0xFDxx`), rien dans le SDK Jieli, rien dans la pile Colmi,
  aucune référence publique. Il renvoie une valeur vide.

- **Le type `0x73` dans l'espace « big data »** : non documenté. Gadgetbridge ne nomme que
  `0x27` (sommeil) et `0x2A` (SpO2), tout le reste tombe dans
  « Received unrecognized big data packet ». À noter, sans en tirer de conclusion : dans
  l'espace de commandes **V1** (l'autre canal), `0x73` est `CMD_NOTIFICATION`. Ce sont deux
  espaces de numérotation distincts ; la coïncidence peut n'en être qu'une.

- **La nature du flux de type `0x59`** (386 trames en 90 s dans le relevé précédent) : à
  reparser avec le bon découpage. À ce rythme (~4 trames/s), ce n'est pas de l'audio :
  le débit est trop faible d'au moins un ordre de grandeur. Télémétrie de capteur, plus
  probablement.

- **La clé d'authentification RCSP de ces lunettes** : inconnue. La clé publiée par le projet
  E87 est celle de leur appareil ; rien ne dit qu'elle est universelle.

## 4. Les trames observées : lecture proposée

```
bc 73 03 00 5e 61   05 56 00
bc 73 03 00 5e 91   05 55 00
bc 73 03 00 5f 01   05 54 00
└┬┘ └┬┘ └─┬─┘ └─┬─┘ └───┬──┘
 │   │    │     │       └── charge utile (3 octets)
 │   │    │     └────────── CRC-16/MODBUS de la charge utile, petit-boutiste  [ÉTABLI]
 │   │    └──────────────── longueur = 3, petit-boutiste                      [ÉTABLI]
 │   └───────────────────── type = 0x73                                       [ÉTABLI]
 └───────────────────────── magie « big data »                                [ÉTABLI]
```

Il n'y a donc **aucun compteur** dans ces trames. Ce que l'on pouvait prendre pour un compteur
croissant en positions 4-5 est le CRC, qui change parce que la charge utile change.

La charge utile est `05 56 00`, puis `05 55 00`, puis `05 54 00`. Le premier octet est stable,
le deuxième décroît de 86 à 84, le troisième est nul.

Or le relevé précédent avait capté, sur ce même type `0x73`, deux autres charges utiles :
`03 01` et `0a 01`. Le premier octet varie donc d'une trame à l'autre. **Structure la plus
cohérente : `[code] [valeur…]`**, avec un code d'événement suivi d'une valeur de longueur
variable.

### Lectures possibles du couple `05` + `56 00`

**a) Batterie — la plus probable.**
`05` = code « niveau de batterie », `0x56` = 86 %, `0x00` = pas en charge.
Arguments :

- La valeur est dans 0-100 et décroît de 1 en 1, sans jamais remonter.
- La forme `[code][niveau][drapeau de charge]` est exactement celle de la réponse batterie du
  canal V1 de la même famille (`03 <niveau> <en charge>`), documentée dans Gadgetbridge et
  dans `colmi_r02_client`.
- L'irrégularité des intervalles (6 s, puis 14 s, puis plus rien pendant 100 s) colle à une
  émission **sur changement** et non périodique : la jauge bouge deux fois puis se stabilise.
  C'est le comportement typique d'une jauge qui se détend juste après le débranchement du
  chargeur, ou en début de décharge.

**b) Une mesure physiologique héritée du module bague.**
86, 85, 84 est une courbe de fréquence cardiaque au repos tout à fait crédible, et le firmware
embarque bel et bien la pile logicielle des bagues Colmi. Contre : des lunettes audio n'ont
normalement pas de capteur optique. Ce serait alors une valeur simulée ou un résidu de module.

**c) Un niveau réglé par l'utilisateur (volume).**
Cohérent avec un pas de exactement -1 et des intervalles irréguliers, si Miguel a effleuré la
branche trois fois. Contre : il n'a rien signalé de tel, et le silence de 100 s qui suit
s'expliquerait mal.

**d) Un décompte (extinction automatique, minuterie de session).**
Peu probable : un décompte temporel perdrait 6 puis 14 unités, pas 1 puis 1.

### Comment trancher, sans aucun risque

Brancher le chargeur pendant que la capture tourne sur `de5bf729`.

- Si l'hypothèse (a) est bonne : le troisième octet passe à `01` et le deuxième se met à
  **croître**. C'est décisif en une minute.
- Si rien ne bouge, relancer la capture en effleurant volume + et volume − : l'hypothèse (c)
  se voit immédiatement.

Et dans les deux cas, corriger d'abord le découpage des trames dans les scripts de capture,
sinon les résultats resteront illisibles.

## 6. Pistes concrètes, de la plus sûre à la plus risquée

> **Avertissement, à lire avant toute manipulation.** Miguel n'a qu'une seule paire de
> lunettes et présente son produit le **8 septembre**. Aucune copie du firmware d'origine
> n'existe. Toute opération qui **écrit** dans la mémoire flash — mise à jour OTA, outil
> `jl-uboot-tool`, commande RCSP de formatage — peut rendre l'appareil définitivement
> inutilisable, sans recours. **Les pistes 6 à 8 ci-dessous sont à proscrire avant le 8
> septembre.** Les pistes 1 à 3 ne présentent aucun risque matériel.

### 1. Aucun risque — utiliser les lunettes comme un casque Bluetooth ordinaire

Les lunettes exposent A2DP (`110B`) pour la sortie et HFP (`111E`) pour le micro. Windows sait
faire les deux nativement. IRIS écoute le micro mains libres pour « Dis-moi Iris » et répond
par la sortie audio. Zéro rétro-ingénierie, zéro écriture dans l'appareil, opérationnel
immédiatement.

Limite connue et à assumer : le micro HFP impose un mode « mains libres » à 8 ou 16 kHz mono
et Windows bascule alors la sortie dans la même qualité dégradée pendant que le micro est
ouvert. C'est audible mais parfaitement suffisant pour la détection de mot-clé et la
transcription. Pour une démo le 8 septembre, **c'est la piste à sécuriser en premier.**

### 2. Aucun risque — écoute passive de tous les canaux de notification

S'abonner en notification à `ae02`, `ae04`, `ae05`, `ae3c`, `de5bf729`, `6e400003`, `fee3`,
`4a02` et journaliser tout, en corrélant avec les actions physiques (appui, effleurement,
branchement du chargeur, mise en charge, appel entrant). C'est de la lecture pure : l'appareil
ne reçoit rien.

À faire en priorité, avec le découpage corrigé de la section 1.6 : c'est ce qui donnera la
table « geste → code » dont IRIS a besoin, et c'est ce qui tranchera la question de la
batterie en une minute (section 4).

### 3. Aucun risque — écoute du port série SPP (COM4)

Ouvrir COM4 en lecture seule et journaliser. Si les lunettes poussent des événements en RCSP
sur SPP, ils commenceront par `FE DC BA` et le format est entièrement documenté ci-dessus.
Aucune écriture, donc aucun risque.

### 4. Risque faible — sonder le canal V1 avec une commande de lecture documentée

Le canal `6e40fff0` / `6e400002` accepte des paquets de **16 octets**, premier octet = type de
commande, dernier octet = somme des 15 premiers modulo 255. La requête de batterie est le type
`0x03`. Si les lunettes répondent, on obtient à la fois le niveau et la confirmation que le
module Oudmon est actif.

C'est une écriture, donc plus tout à fait gratuit, mais la commande est banale et documentée.
**À ne jamais envoyer au hasard dans cet espace** : `0x08` = extinction,
`0xFF` = remise en configuration d'usine. N'envoyer que `0x03`.

### 5. Risque faible à modéré — sonder le canal V2 « big data »

Écrire sur `de5bf72a` une trame `BC <type> <len> <CRC> <charge utile>` avec le CRC-16/MODBUS
correct. Commencer par reproduire la requête SpO2 de Gadgetbridge (`bc 2a 01 00 ff 00 ff`),
qui est un pur appel de lecture d'historique : soit l'appareil répond, soit il ignore. Ne pas
balayer les types au hasard : on ne sait pas ce que fait le firmware des lunettes sur un type
inconnu, et rien ne garantit qu'il se contente de l'ignorer comme le fait une bague.

### 6. Risque modéré — RCSP en lecture sur SPP

Construire des trames `FE DC BA | 0xC0 | opcode | longueur | corps | EF` avec des opcodes de
lecture seule : `0x02` (carte des fonctions), `0x07` (lecture d'information système). Le gain
serait réel : version de protocole, type de SDK, VID/PID, code produit, MTU, statut de mise à
jour, présence d'une double partition.

Deux réserves sérieuses. D'abord l'authentification RCSP peut bloquer l'accès, et la
contourner suppose de reprendre le travail sur `libjl_auth.so`. Ensuite, **le même espace
d'opcodes contient `0x22` (formatage de l'appareil), `0x1F` (suppression de fichier) et
`0x20` (renommage)** : une erreur d'un octet dans l'opcode a des conséquences
irréversibles. À faire uniquement après la démo, avec une table d'opcodes autorisés codée en
dur dans l'outil et un refus explicite de tout le reste.

### 7. Risque élevé — mise à jour OTA

Ne pas lancer d'OTA. Ni avec l'application Jieli générique, ni avec l'application Play tierce,
ni avec un fichier `.ufw` trouvé ailleurs. Le mécanisme OTA de Jieli écrase la flash ; un
firmware destiné à un autre modèle transforme les lunettes en presse-papier, et il n'existe
aucune sauvegarde du firmware d'origine. **À proscrire absolument avant le 8 septembre**, et
même après, seulement avec un firmware fourni par le fabricant pour cette référence précise.

### 8. Risque très élevé — lecture ou écriture directe de la flash

`jl-uboot-tool` sait lire et écrire la flash d'une puce Jieli, ce qui permettrait de
sauvegarder le firmware d'origine — le seul filet de sécurité qui manque aujourd'hui. Mais :

- il faut un accès USB aux broches D+/D− de la puce, et le relevé précédent n'a rien vu en USB
  avec le câble fourni ;
- l'entrée en mode UBOOT exige d'injecter une séquence `USB_KEY` (0x16EF) sur les lignes USB,
  avec un bus isolé de tout autre périphérique ;
- l'auteur signale lui-même un risque de court-circuiter des sorties à la masse pendant
  l'échantillonnage de l'ACK, des faux positifs de détection, et un effacement qui « peut ne
  pas fonctionner correctement » si l'adresse n'est pas alignée sur une limite de bloc ;
- la compatibilité annoncée est « réalistement » AC690–AC696N, et la puce des lunettes n'est
  pas identifiée avec cette précision.

Concrètement, cela suppose d'ouvrir la monture et de souder. **À ne pas tenter sur l'unique
exemplaire.** Si cette voie devient nécessaire, acheter une seconde paire identique et
travailler dessus.

### Recommandation

Pour le 8 septembre : **pistes 1, 2 et 3 uniquement.** Le casque Bluetooth standard suffit à
faire fonctionner IRIS sur les lunettes, et l'écoute passive avec le découpage corrigé donne
la table des gestes sans jamais écrire un octet dans l'appareil.

Après la démo, et seulement après : piste 4, puis 5, puis 6 avec une liste blanche d'opcodes.

Une remarque de fond, valable pour la suite du produit. Remplacer le firmware de ces lunettes
n'est pas un problème technique mais un problème de fournisseur : Jieli distribue son SDK, ses
outils et ses clés à ses clients industriels, pas au public. La voie propre passe par une
relation commerciale avec l'ODM — c'est ce que disait déjà `LUNETTES-DIAGNOSTIC.md`, et rien
dans cette recherche ne le contredit.
